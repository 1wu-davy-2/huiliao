# 功能扩展方向（5 个候选）

> 2026-08-10 记录。本文档只列方向、前置条件与风险，不构成已批准的实施计划。
> 每个方向的「硬阻塞」是动工前必须先解掉的事项，不是可选项。

## 汇总

| # | 方向 | 价值 | 规模 | 硬阻塞 |
|---|------|------|------|--------|
| 一 | AI 试炼场接入主训练流 | 高 | 大 | 服务端题目审核门；本地优先不变量 |
| 二 | 复盘与进度从记录升级为教学 | 高 | 中 | **`progress` 不存历史，需 v3→v4 迁移** |
| 三 | 落地页改为「先试后进入」 | 中高 | 中 | 无 |
| 四 | 情境内容作者工具链 | 中 | 中大 | 需先定产物形态（浏览器无写盘权限） |
| 五 | 练习节奏与间隔重复 | 中低 | 中 | 同方向二；且与产品原则冲突 |

建议顺序：**三 → 二 → 一 → 四 → 五**。方向三无硬阻塞，且顺带解掉落地页三个既有问题；
方向二的存储迁移是方向五的前置，先做可避免二次迁移。

## 全局约束（任一方向都不得违反）

- **静态半边必须能在函数不可达时照常工作。** AI 试炼是唯一网络出口，由用户主动触发、
  用用户自己的密钥。任何把模型调用塞进情境练习主路径的设计，都必须显式 opt-in，
  且在失败时优雅降级回预设选项。
- **服务端题目审核门。** `api/_lib/challenges.ts` 的 `hasReviewedPool()` 拒绝任何未审校
  `challengeId`。生产题池为空，因此依赖 `/api/ai/*` 的新功能在内容审校通过前都不可用——
  这是发布门，不是绕过对象。
- **自由文本不落盘。** 草稿与自由输入不持久化；新增分析能力时不要顺手把原文写进存储。
- **内容变更必须保 Zod 校验**，并补边界相关回归测试。

## 方向一 · AI 试炼场接入主训练流

**目标**：情境练习在任意节点可「转为自由对话」——模型接管对方角色，用户脱离预设选项自由
回应，仍由本地 `analyzeMessage` 出五维诊断。练完可回到原分支树继续。

**现状与差距**

- 静态分支树（`src/content/scenarios-*.ts` + `ScenarioPage`）与 AI 试炼场（`/lab/ai`）
  是两条完全无交集的路径。
- 刚落地的 AI 配置（`aiConfig`）目前只有 `/lab/ai` 一处消费，覆盖面过窄。
- 情境节点的 `choices` 是写死的，用户无法用自己的话回应（自由输入只在消息实验室有）。

**实施要点**

- `ScenarioPage` 每个节点加「用自己的话说」入口；进入后渲染一个轮次受限的对话区。
- 系统提示需按**情境角色 + 当前节点上下文**构建，且仍必须服务端生成
  （`buildSystemPrompt` 不接受客户端传入的 prompt）。
- 用户输入先过 `safetyCheck`，`blocked` 直接拦下不发请求——`AiTrialPage` 已有此前置，照抄。
- 退出自由对话时回到原节点，不污染分支树状态；`ProgressRecord.attempts` 的计数口径要想清楚。

**硬阻塞**

1. **题目审核门。** 基于情境的自由对话没有 `challengeId`，现有 `/api/ai/turn` 会拒。
   需要服务端改动：新增端点，或扩展 `turn.ts` 支持「情境上下文模式」并为其设计等价的
   内容门禁。**不要用 `_DEV_DEMO` 的 id 蒙过去**——那是 dev-only 注入。
2. **本地优先不变量。** 情境练习目前完全离线。此改动给主训练路径引入网络依赖，
   必须严格 opt-in（未配置 `aiConfig` 时入口不出现），且请求失败时能退回预设选项继续。

**风险**

- 自由对话让模型扮演拒绝/迟疑角色，输出不受控。安全分类器只管用户输入，**不管模型输出**；
  需要决定是否也对模型回复做检查，以及检查失败时怎么呈现。
- 消耗用户 Token。必须在入口处披露，不能静默发请求。

**规模**：大。服务端 + `ScenarioPage` + 新对话组件 + 安全策略决策。

## 方向二 · 复盘与进度从「记录」升级为「教学」

**目标**：跨会话能力趋势、同类情境历次表达对比、从边界失误反推薄弱项。

**现状与差距**

- `reflections` 只存 `{id, scenarioId, createdAt, text}`，无任何结构化分析。
- `aggregateSkillScores` 只出**当前均值**，是一个快照。
- `boundaryAccuracy` 已算出通过率，但 UI 未用它做任何归因。

**硬阻塞：`progress` 不是历史日志**

`addProgressRecord`（`storage.ts`）按 `scenarioId` **查找并覆盖**同一条记录：

```ts
const existingIndex = data.progress.findIndex((r) => r.scenarioId === record.scenarioId)
if (existingIndex >= 0) data.progress[existingIndex] = parsedRecord
else data.progress.unshift(parsedRecord)
```

所以每个情境只留最后一次结果，重练即抹掉上一次。**趋势线无法从现有数据构建**——
不是加个图表就行，得先把 `progress` 改成追加式历史（或另开 `progressHistory`），
即 `SCHEMA_VERSION` v3→v4 迁移。迁移策略需决定：旧的单条记录视为历史第一条。

**实施要点**

- 迁移后 `progress` 语义变化，所有读取方（`HomePage`、`ProgressPage`、`skills.ts`）都要跟着改。
- 趋势计算放 `src/lib/skills/`，保持纯函数、可单测。
- 「同类情境」需要一个归类维度——`purpose` 或 `stage` 都可以，但要先定，别两处各用一套。

**风险**：追加式存储会持续增长，需要和 `trialSummaries` 一样的上限与淘汰策略。

**规模**：中。核心成本在迁移与读取方连带改动，分析本身不难。

## 方向三 · 落地页改为「先试后进入」

**目标**：落地页嵌一个可交互的消息诊断迷你 demo——粘一句草稿立刻出五维诊断，
不需要过 onboarding。用真实功能替掉手写截图。

**现状与差距**

- `LandingPage.tsx:56-127` 是**手写 DOM 复刻的 HomePage**：侧栏四项、topbar
  「/ 训练工作台」、标题「今天练哪一场？」、五个快捷 chip、五维能力条硬编码
  `62/78/48/55/71`。会随真实 UI 漂移，且假数据看起来像真数据，无测试守。
- 文案定位错配：落地页讲「职场/人际沟通」（清晰表达 / 边界意识 / 冲突处理、
  「非暴力沟通技巧」），实际内容是**成年人约会与关系沟通**（初次聊天、邀约、被拒绝、
  同意确认，草稿含情趣边界）。
- 三个 CTA 都不提 18+，而 `/onboarding` 第 0 步强制勾选年满 18 岁。

**为什么技术上零障碍**

`analyzeMessage` 是纯函数，无网络、无存储依赖，安全检查也在本地。当前构建只产出单个
`index-*.js`（无路由分包），`analyze.ts` 已在包内，落地页引用它**不增加额外体积**。

**实施要点**

- demo 输入不落盘（与消息实验室同口径：草稿不持久化）。
- `analyzeMessage` 需要 `context` 参数，形状应与 `MessageLabPage` 构造的一致——
  复用而非另起一套，否则两处诊断结论会不一致。
- 同步修正文案定位与 18+ 披露（见下方修复计划，两件事一起做成本更低）。

**规模**：中。删 70 行手写 mockup、接一个已有纯函数、改文案。

## 方向四 · 情境内容作者工具链

**目标**：可视化编排节点图、实时跑 `validateScenarioCorpus()` 提示违规、导出合规 TS 模块。
让审校者能自己改内容，不必回来提 issue。

**现状与差距**

- s14–s21 与 18 道 AI 题全卡在人工审校，**瓶颈是内容产出不是代码**。
- `validateScenarioCorpus()` 已能查可达性、死路、环、危险选项缺边界提示、
  危险路径通向 mutual 结局——但只在 import 时抛错，作者拿不到可视反馈。

**硬阻塞：产物形态要先定**

浏览器无写盘权限，三条路各有代价：

| 方案 | 优点 | 代价 |
|------|------|------|
| dev-only 路由 + 导出下载 | 复用现有校验与类型 | 作者要手动放文件；须确保不进生产包 |
| Node CLI（`scripts/`） | 直接写盘 | 无可视化，仍是编辑代码 |
| dev 路由导出 JSON + 脚本转 TS | 两边优点 | 两段流程，需维护 JSON↔TS 转换 |

**风险**：dev-only 路由若泄进生产包，等于把内容编辑器交给所有用户。
`verify-deploy.mjs` 目前扫的是草稿文案标记，**不扫路由**，需要新增守卫。

**规模**：中大。价值取决于审校者是否真的会用——建议先问过审校方再动工。

## 方向五 · 练习节奏与间隔重复

**目标**：按边界失误率决定哪类情境该复练、何时复练，配合 Notification API 本地提醒。

**硬阻塞**

1. **同方向二**：需要历史记录才能算失误率趋势，当前 `progress` 覆盖式存储不支持。
   应在方向二的迁移中一并考虑，避免二次迁移。
2. **与产品原则冲突。** 产品第 5 条原则是「不确定就放慢」，README 明确不承诺任何关系结果。
   streak／连续打卡／推送催促都与此相悖。若做，必须是**用户主动开启**的温和提醒，
   不设连续中断惩罚，不展示「你已断签 N 天」。

**实施要点**

- Notification API 需权限提示，且权限被拒后功能要静默失效而非反复索取。
- 无服务端，提醒只能在页面打开时调度，实际到达率有限——这点要对用户说清楚，
  不要暗示这是可靠的日程提醒。

**规模**：中。技术不难，产品判断难。
